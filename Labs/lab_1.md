# Лабораторная работа №1. Разработка сервиса на FastAPI

## Цель работы

Научиться:

1. разворачивать и документировать REST API для машинного обучения с помощью FastAPI;
2. использовать pre-commit hooks для автоматической проверки качества кода;
3. писать тесты для проверки работы API и модели по методике TDD;
4. работать с виртуальным окружением и зависимостями.

Модель для инференса: [`s-nlp/russian_toxicity_classifier`](https://huggingface.co/s-nlp/russian_toxicity_classifier) — классификация русских текстов на токсичность. Можете взять любую другую модель/задачу. 

## Ход работы

### 1. Репозиторий и окружение

1. Создайте репозиторий на GitHub.
2. Склонируйте репозиторий локально.
3. Заведите структуру проекта:

```
ml_app/
├── app/
│   ├── main.py
│   ├── model.py
│   └── schemas.py
├── tests/
│   └── test_api.py
├── requirements.txt
├── .pre-commit-config.yaml
└── README.md
```

Структура ориентировочная — если удобнее по-другому, не принципиально, но разделение "приложение / тесты / зависимости" должно сохраняться.

4. Виртуальное окружение (venv, poetry/uv, любое другое на выбор):

```bash
python3 -m venv venv
source venv/bin/activate
```

5. `requirements.txt`:

```
# --- API ---
fastapi
uvicorn

# --- NLP ---
transformers
torch

# --- Validation / Schemas ---
pydantic

# --- Testing ---
pytest
httpx
requests

# --- Code quality ---
black
flake8
isort
mypy
pre-commit
```

### 2. Pre-commit

Настройте `.pre-commit-config.yaml` с как минимум тремя хуками (например `black` -- форматтер, `flake8` -- линтер, `isort` -- сортировка импортов). Проверьте, что хуки реально блокируют коммит с ошибками — например, нарушьте PEP8 и убедитесь, что коммит не проходит.

### 3. TDD

По методике TDD тесты пишутся **до** реализации эндпоинтов. Напишите 5 тестов на pytest в `tests/test_api.py`. Примеры кейсов:

- `/health` возвращает 200 и корректный статус;
- `/predict` возвращает валидную схему ответа (класс + вероятность);
- `/predict_batch` корректно обрабатывает список из нескольких текстов;
- `/predict_batch` не падает на пустом списке.

Структура и кейсы — на ваше усмотрение, но каждый тест должен проверять что-то конкретное, не быть тавтологией вида "функция вызывается и не падает без проверки результата".

### 4. Реализация сервиса

Эндпоинты:

- `GET /health` — проверяем что сервис жив;
- `POST /predict` — предсказание для одного текста;
- `POST /predict_batch` — предсказание для списка текстов (длина не фиксирована);
- `GET /model_info` — метаданные модели (название, версия библиотеки, размер, что сочтёте нужным).

Схемы запросов/ответов — через Pydantic (`app/schemas.py`).

### 5. Запуск и проверка

```bash
uvicorn app.main:app --reload
pytest tests/ -v
```

**Важно:** не пушьте веса модели в репозиторий — они скачиваются из HuggingFace при старте сервиса. Если нужно закешировать локально — добавьте кеш в `.gitignore`.

## Примерные вопросы
Что нужно уметь объяснить на сдаче?

1. Зачем нужны линтеры/форматтеры/type hints, чем автоматизация проверки кода лучше ручного код-ревью?
2. Как работает pre-commit hook (когда запускается, что может заблокировать)?
3. Принцип TDD: зачем писать тесты до кода, какие виды тестов бывают (например unit, интеграционные, т.д.).
4. Можно ли хранить веса модели в git? Какие есть альтернативы?
5. End-to-end работа приложения на FastAPI (уметь объяснить как работает ваш сервис)
